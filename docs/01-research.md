# 01 — Исследование: пределы возможного для ИИ-браузера

Дата среза: сентябрь 2026. Все факты о рынке ниже взяты из открытых источников на момент среза
(ссылки в конце разделов); рынок меняется каждые несколько месяцев, поэтому документ надо
перечитывать при каждом крупном решении. Формулировки вида «X делает Y» — это состояние продукта
на дату среза, а не вечная истина.

Исходные параметры проекта (заданы пользователем, зафиксированы здесь как ограничения):

| Параметр | Значение |
|---|---|
| Платформы | Windows (десктоп) — первая; iOS — вторая |
| Аудитория | разработчики |
| ИИ-модели | гибрид, приоритет локальных для приватных данных |
| Целевое железо | ~8 ГБ RAM, GPU класса RTX 4060 (8 ГБ VRAM); iPhone с Apple Intelligence |
| Жёсткие ограничения | только open-source лицензии в нашем коде и зависимостях, которые мы ставим сами; никакой телеметрии |
| Стек | выбирается в этом документе (см. §6, ADR-002) |

### 1.2. Выводы из ландшафта

1. **Standalone AI-браузер как продукт большой компании не выстрелил** (Atlas закрыт через 9 месяцев;
   Operator — через 7; Dia куплена и переориентирована на enterprise). Выжили: (а) агент как
   слой в существующем браузере (Chrome, Edge, Brave, Claude for Chrome), (б) Comet как бесплатный
   research-браузер. Для нас это значит: ценность не в «ещё одном Chromium с чатом», а в
   **ядре, где ИИ встроен в модель данных браузера** (история, вкладки, DOM, сеть) — и в честной
   безопасности, которой у лидеров нет.
2. **Главная нерешённая проблема категории — indirect prompt injection + отказ от same-origin
   policy.** Исследование UW (7 браузеров, янв–фев 2026): в наименее ограниченных браузерах SOP
   сводится к «стойкости модели к инъекциям», а OpenAI официально признал, что идеальной
   модельной защиты не существует. Все успешные атаки Zenity используют один факт: **агент —
   единая сущность над множеством авторизованных вкладок**, то есть воскрешённый CSRF.
   Единственные подходы, которые сработали хоть частично: **архитектурные** (Dia: структурно
   запретить класс выходов; Brave: изолированный профиль + второй проверяющий LLM + запрет
   внутренних страниц; Atlas: блок localhost/ФС/URL-классификаторы — и всё равно взломан).
3. **Локальный ИИ в браузерах почти не используется по назначению.** Gemini Nano — только для
   скам-детекции; Brave BYOM — для энтузиастов; Apple — единственный, кто делает системный
   on-device LLM платформенной нормой. Ниша «приватный-по-умолчанию агент с локальным
   инференсом на потребительской GPU» **свободна**.
4. **Пользовательская критика повторяется**: (а) «не доверяю агенту банковские вкладки», (б)
   контекст страниц уходит на сервер и хранится (Comet 30 дней), (в) платные лимиты на
   задачи (Chrome 20/день), (г) скрытые компоненты (Comet — два невидимых расширения), (д)
   агент медленный и падает на CAPTCHA/сложных JS-флоу, (е) отсутствие Windows-версий (Dia).
5. **Инструментальная экономия токенов решает** — agent-browser в 50–100 раз дешевле Playwright
   MCP по токенам за счёт компактных снимков; Browser Use — за счёт DOM-дистилляции. Формат
   наблюдения страницы — это архитектурное решение первого порядка (см. §2.1 и ADR-006).
6. **Появляется стандарт кооперации сайтов с агентами (WebMCP)**. Нужно поддержать его как
   предпочтительный путь актуации, с fallback на DOM.

## 2. Пределы возможного: полный список ИИ-возможностей по слоям

Легенда приоритета: **P0** — ядро первого релиза; **P1** — второй релиз; **P2** — исследовательское.
Для каждой возможности — ограничение (стоимость/задержка/память/риск), детали в §3.

### 2.1. Понимание страницы (Page Intelligence)

| # | Возможность | P | Как | Ограничение |
|---|---|---|---|---|
| PI-1 | Семантический снимок DOM: accessibility-tree + видимость + интерактивность → компактное дерево (≤2–4K токенов) с стабильными `ref`-идентификаторами элементов | P0 | Инжектируемый JS-сенсор + CDP `Accessibility.getFullAXTree`/`DOM` на десктопе; только JS на WKWebView | Формат снимка — главный рычаг стоимости; shadow DOM и cross-origin iframe требуют отдельной политики (см. безопасность) |
| PI-2 | Извлечение основного контента (readability), удаление шума | P0 | Детерминированные алгоритмы (Readability/Trafilatura-подобные), без LLM | Ошибки на SPA; нужна пере-экстракция по мутациям |
| PI-3 | Структурированное извлечение (цены, даты, характеристики, таблицы) по JSON-схеме | P0 | Локальный 4B с constrained decoding (GBNF-грамматика в llama.cpp) | 1–3 с на страницу локально; галлюцинации при отсутствии данных → обязательные `null` и цитаты-источники |

### 2.3. Действия (Agent Runtime)

| # | Возможность | P | Как | Ограничение |
|---|---|---|---|---|
| A-1 | Многошаговые задачи на сайтах: формы, поиск, сравнение, сбор данных в таблицу | P0 | Планировщик (LLM) → инструменты `navigate/click/type/select/extract/scroll/wait` по `ref` из снимка PI-1 | Успех 60–90% на бенчмарках у лидеров; у локального 8B ниже → облачная модель как опция для планирования без утечки приватных данных (см. маршрутизацию) |
| A-2 | Изолированный агентный профиль по умолчанию + явный импорт сессии на конкретный origin | P0 | Отдельный профиль/`request context`; перенос cookie домена только по подтверждению на задачу | Часть задач требует логина — трение, но это цена SOP |
| A-3 | Обязательные подтверждения необратимых действий (оплата, отправка, удаление, публикация, загрузка файлов) с превью | P0 | Классификатор действий по правилам + `consequentialHint` WebMCP + модель | Ложные срабатывания раздражают → уровни доверия per-site как у Edge (Strict/Balanced) |
| A-4 | «Сухой прогон»: план и все шаги до первого необратимого — с показом, что будет сделано | P0 | Режим исполнения `dry_run` в рантайме | — |
| A-5 | Журнал действий с воспроизводимостью, откатом там, где возможен | P0 | Append-only `agent_actions` + снимки до/после | Откат чаще всего невозможен на сайте — только «инструкция как отменить» |

## 3. Технические ограничения по возможностям

### 3.1. Стоимость и задержки инференса на целевом железе

Целевая десктоп-конфигурация: 8 ГБ системной RAM, RTX 4060 8 ГБ VRAM (272 ГБ/с). Ключевой факт:
**системной RAM мало, а VRAM относительно много** — значит, модели должны целиком жить в VRAM,
а системная память отдана браузеру (Chromium с 15 вкладками — 2–4 ГБ).

Ориентиры (открытые бенчмарки 2026 г., llama.cpp, Q4_K_M):

| Модель | Вес Q4_K_M | VRAM с KV 8K | Decode на 4060 | Роль |
|---|---|---|---|---|
| Qwen3-4B | ~2.5 ГБ | ~3.5 ГБ | ~70–90 tok/s | «быстрая»: суммаризация, извлечение, классификация, критик |
| Qwen3-8B | ~5.0 ГБ | ~6.0–6.5 ГБ | ~40 tok/s | «умная»: планирование агента, Q&A |
| Phi-4-mini 3.8B | ~2.5 ГБ | ~3.2 ГБ | ~28 tok/s (по отзывам 4060) | CPU-fallback без GPU (15–20 tok/s CPU) |
| Gemma 4 E4B (мультимодальная) | ~6 ГБ | тесно | 40–60 tok/s | картинки по требованию |
| Gemma 4 12B QAT Q4_0 | 6.98 ГБ | ~1 ГБ на KV — предел | — | не для 8 ГБ по умолчанию |
| EmbeddingGemma-300M | <200 МБ | — | тысячи tok/s | эмбеддинги (100+ языков, MRL 768→128) |
| Qwen3-Embedding-0.6B | ~640 МБ | — | — | «качественные» эмбеддинги, 32K контекст |

Расчёт бюджета «суммаризация страницы < 3 с» для Qwen3-4B: prefill 3 000 токенов ≈ 1.0–1.5 с на
4060 + 150 токенов вывода при 80 tok/s ≈ 1.9 с → **укладывается** только на 4B-модели с уже
загруженными весами (загрузка 2.5 ГБ с NVMe ≈ 1–2 с, поэтому «быстрая» модель резидентна, «умная»
подгружается по требованию и выгружается по таймауту). На 8B суммаризация ≈ 4–5 с → не проходит
бюджет, используется только для планирования.

Одновременно в 8 ГБ VRAM помещаются: 4B (3.5 ГБ) + эмбеддер (0.3 ГБ) + запас композитору/GPU
Chromium (~1.5 ГБ). **4B + 8B одновременно — нет**; переключение через выгрузку (llama-server с
несколькими моделями и LRU).

iOS: системный LLM Apple (~3B) через Foundation Models — бесплатен по памяти для приложения;
собственные модели — llama.cpp/Metal ≤ 1.7B (Qwen3-1.7B Q4 ≈ 1.1 ГБ) или Core ML/Core AI (iOS 27);
эмбеддер EmbeddingGemma в Core ML.

Облако (только по явной политике): планирование агента фронтир-моделью снижает число шагов и
ошибок, но каждый снимок страницы 2–4K токенов × 10–30 шагов = 40–120K токенов на задачу; при
$3/M вход ≈ $0.1–0.4 за задачу. Это то, за что Chrome берёт $20/мес за 20 задач/день.

### 3.2. Память и диск

## 4. Выбор движка

### 4.1. Критерии и веса

Контекст: маленькая команда разработчиков; Windows первым, iOS вторым; нужна максимальная
итерационная скорость; ИИ-агенту нужен низкоуровневый доступ (DOM, accessibility-tree, сеть,
ввод); совместимость с расширениями желательна; никакой телеметрии; open source.

**Жёсткое ограничение iOS**: Apple требует WebKit для всех браузеров глобально; альтернативные
движки разрешены только в ЕС через BrowserEngineKit с отдельным EU-бинарём, `arm64e`, потерей
существующих пользователей — за ~2.5 года **ни один вендор не выпустил** ничего на этой базе.
Следовательно, iOS = **WKWebView, без вариантов**, и архитектура обязана работать поверх двух
движков. Это делает «адаптер движка» не абстракцией впрок, а требованием первого дня.

|---|---|---|---|---|---|---|---|---|---|

### 4.3. Решение

**Десктоп: Chromium через CEF (Chrome-bootstrap) с Rust-биндингами; iOS: WKWebView; общее ядро на Rust;
единый `EngineAdapter` с тремя реализациями: `cef`, `wkwebview`, `cdp-remote` (любой Chromium по CDP —
для headless-песочницы агента и e2e-тестов).** Форк Chromium отвергнут по стоимости поддержки,
Electron — из-за Node в процессе и слабых расширений, WebView2 — как основной, потому что движок
закрытый и его жизненный цикл/расширения контролирует Microsoft (остаётся **резервным** бэкендом
адаптера: CDP-семантика почти та же), Qt WebEngine — из-за отставания версий, Servo — из-за
незрелости (мониторим), Playwright-обёртка — не продукт.

Подробное обоснование, последствия и план миграции — ADR-001.

|---|---|---|
| Быстрая (суммаризация, извлечение, критик, интент) | Qwen3-4B Q4_K_M (резидентна) | Apple Foundation Models (системная ~3B) |
| Умная (планирование агента, Q&A) | Qwen3-8B Q4_K_M (по требованию, LRU) | Foundation Models; облако по политике |
| Мультимодальная | Gemma 4 E4B (по требованию) | Vision framework + Foundation Models |
| Эмбеддинги | EmbeddingGemma-300M, 256-dim (MRL) — общий формат векторов на обеих платформах | EmbeddingGemma-300M через Core ML |
| ASR | whisper.cpp small | Speech framework |
| CPU-fallback без GPU | Phi-4-mini или Qwen3-4B на CPU (15–20 tok/s) | — |

Единый эмбеддер и размерность на обеих платформах — требование для будущей синхронизации памяти (M-7).

### 5.3. Облачные провайдеры

Единый адаптер `ModelProvider` (чат с инструментами, стриминг, JSON-schema/грамматика, эмбеддинги):
реализации `LlamaServer`, `Ollama`, `OpenAICompatible` (покрывает OpenAI, OpenRouter, vLLM, LM Studio),
`Anthropic`, `Gemini`, `AppleFoundationModels`. BYOK, выключено по умолчанию, ключи в OS keychain.

### 5.4. Эмбеддинги и векторное хранилище

| Вариант | Плюсы | Минусы |
|---|---|---|
| **SQLite + sqlite-vec + FTS5** | Одна файл-БД вместе с историей/сессиями агента; транзакции и каскадные удаления; гибридный поиск через FTS5; <1 МБ расширение; работает на iOS | Только точный brute-force KNN (ANN не выпущен); практический предел ~250–500K векторов |
| LanceDB | ANN (IVF-PQ/HNSW), версионирование (time-travel — полезно для аудита памяти агента), больше-чем-RAM, гибрид BM25 | Каталог файлов, отдельная транзакционная модель от SQLite, pre-1.0, тяжелее на iOS |
| Qdrant embedded | Полноценный ANN | Отдельная модель хранения, оверкилл для single-user |

**Решение**: SQLite + sqlite-vec + FTS5 как единственное хранилище (ADR-004). Партиционирование
по времени/домену держит поиск < 50 мс; квантование int8; при росте > 500K чанков — миграция
индекса чанков в LanceDB (данные остаются в SQLite; интерфейс `VectorIndex` абстрагирован).

### 5.5. Маршрутизация запросов по чувствительности

Каждый входной артефакт запроса помечается классом (метки вычисляются детерминированно, не моделью):

| Класс | Примеры | Куда можно |
|---|---|---|
| `secret` | значения маскированных полей, cookies, токены, тела запросов с Authorization | **никуда** (даже локальной модели не отдаются) |
| `private` | содержимое страниц за логином, почта, документы, история, память пользователя, DevTools-трафик | только локальные провайдеры |
| `personal` | реплики пользователя, содержащие личные данные (детектор PII) | локально; облако только с явным переключателем на запрос |
| `public` | содержимое публичных страниц без логина, общие вопросы | локально по умолчанию; облако — если пользователь включил «облачное планирование» |

Правило композиции: класс запроса = максимум классов его частей. Пользователь видит класс и
провайдера у каждого ответа. Полный офлайн-режим форсирует «локально» для всего.

### 6.1. Что мы сознательно НЕ делаем в первом релизе

- Не строим свой облачный бэкенд, аккаунты и синхронизацию (нет серверов = нет телеметрии и утечек).
- Не даём агенту фоновые задачи с побочными эффектами (только read-only рутины, P1).
- Не поддерживаем macOS/Linux десктоп в первом релизе (CEF позволит позже без изменений ядра).
- Не пытаемся обойти CAPTCHA/анти-бот — агент останавливается и передаёт управление пользователю.
- Не вводим платёжные данные агентом; только автозаполнение браузера после подтверждения человеком.
